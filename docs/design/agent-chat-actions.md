# 需求对话里让 agent 帮你做事（agent-chat-actions）

## 目标

需求对话页原来只能整理需求、确认后建任务。现在你还可以在对话里说「新增产品线」「新建项目」「邀请成员」，助手会先给你一张**确认卡**，你点「确认」才执行。

三条底线：

1. **agent 只能提议，不能执行。** 模型输出的操作只是一条提议。服务端会重新校验参数，只保留白名单字段，再存成待确认卡片。
2. **执行时用你自己的身份和权限。** 确认时用当前登录用户和他在当前工作区的角色，走现有服务的权限检查，绝不提权。你没权限的操作，卡片会保留，可以让有权限的人来确认。
3. **每一步都写审计。** 执行、被拒、失败、取消都会写审计事件，记录操作人、参数和结果。

## 操作分三类

### A 类：确认卡确认后，agent 直接执行

| 操作 | 谁能确认 | 复用的权限检查 | 需要确认 | 审计事件 |
|---|---|---|---|---|
| 新增需求（原有） | 成员及以上 | 原有草稿确认流程（预检、流程计划审批） | 是（需求卡上的「确认创建任务」） | `CHAT_CONFIRMED` |
| 新增产品线 `create_product_line` | 所有者 / 管理员 | 与 `POST /api/product-lines` 一样（`requireManager`） | 是 | `CHAT_ACTION_EXECUTED` |
| 新增项目 `create_project`（放在某条产品线下，可选绑定仓库） | 所有者 / 管理员 | 与 `POST /api/product-lines/{id}/projects` 一样，并复用 `ProjectRepo.create` 的校验（已归档产品线、仓库重复绑定等） | 是 | `CHAT_ACTION_EXECUTED` |
| 邀请成员 `invite_member`（指定角色，可选指定 GitHub 账号） | 所有者 / 管理员；**邀请管理员只有所有者能做** | 直接调用 `MemberService.invite`，规则与成员页完全一致 | 是 | `WORKSPACE_INVITE_CREATED` 和 `CHAT_ACTION_EXECUTED` |
| 查询状态（项目、产品线、相似任务、风险） | 任何成员 | 原有只读工具，限定在当前工作区 | 否（只读） | 工具调用摘要存进对话记录 |

没权限时卡片保持「待确认」，同时写一条 `CHAT_ACTION_DENIED`。参数在执行时变得不合法（比如产品线刚被归档），卡片会标成「失败」，写 `CHAT_ACTION_FAILED`，并在对话里说明原因。

### B 类：agent 只说明或给链接，你到界面上自己操作

这些操作不可逆、会提权，或者涉及钱和密钥，不放进对话：

- 删除或归档产品线、项目、任务、对话
- 改成员角色、移出成员、转让所有者（提升为管理员也算）
- 改预算或配额
- 合并审批、发布、流程计划里放松项的审批（仍走原有审批按钮）
- 模型供应商、密钥、集成凭据、通知渠道等配置
- 治理配置（自治等级、风险规则）

助手会告诉你去哪个页面操作。服务端也不认这些操作：模型就算输出了，也会被拒绝，不会生成卡片。

### C 类：不支持

- 跨工作区操作（只能操作当前工作区）
- 平台管理员功能（工作区配额、暂停工作区）
- 直接改仓库代码或跑命令（这些走任务流水线）
- 代替别人接受邀请

## 「邀请到项目」怎么处理

现在成员和权限是按**工作区**算的，没有项目级成员。所以邀请卡上可以写「想加入的项目」，这一项只作说明，被邀请的人加入的是整个工作区，角色也在工作区生效。如果以后要做项目级权限，需要另外设计。

## 流程

1. 你发一条消息。
2. 先看是不是明确的命令句式，比如「新增产品线 教育」「新建项目 官网 到产品线 教育 仓库 acme/site」「邀请 @octocat 为成员」。是的话**不调用模型**，直接生成确认卡。所以离线、只记录模式、模型不可用时也能用。
3. 其它消息交给模型。模型在输出里加 `actions` 数组提议操作，每轮最多 2 个。服务端按白名单校验并规范化参数：名称长度、角色只能是 admin、member 或 viewer、仓库格式为 owner/name、产品线必须在当前工作区。不合法的提议会作为工具错误反馈给模型，不会生成卡片。每个对话最多同时有 5 张待确认卡片。
4. 卡片通过 SSE 的 `action` 事件推给前端，显示中文参数、「确认」和「取消」。
5. 你点确认，调用 `POST /api/chats/{id}/actions/{aid}/confirm`，服务端用你的身份执行。
   - **幂等：** 同一张卡片重复确认，只返回第一次的结果，不会重复创建。
   - **邀请令牌只返回一次：** 令牌只在确认响应里返回，前端拼成邀请链接显示并复制；数据库和对话记录里都不保存。
6. 执行结果作为一条助手消息写进对话。

## 数据

新表 `chat_action`（V31），字段有：id、对话、工作区、类型、规范化后的参数、状态（proposed、executed、cancelled、failed）、结果、错误、提议来源（agent 或 rules）、确认人、时间。PostgreSQL 上加了行级安全（V32），和其它对话表一样。删除对话时，这个对话的卡片一起删掉；审计事件保留。

## 以后可以做

- 「编辑需求」：现在你可以直接改右侧需求卡，模型也能改草稿。如果要改**已创建的任务**，可以做成 A 类卡片。
- 项目级成员和权限。
- 批量邀请。
