# 可恢复交付流程

2026-10-28：执行错误只结束本次尝试，交付任务保留在原节点，自动处理耗尽后等待明确恢复。本决策覆盖原自治决策中“禁区命中、自愈耗尽、降级 D3 自动废弃”的终止规则。

## 状态与边界

- `currentStage/currentNode` 表示真实流程位置；错误不迁入虚构的异常节点。
- `executionState=BLOCKED/WAITING_INPUT/RECOVERY_REQUIRED` 表示停止，`next_run_at=NULL`，不轮询或重复消耗模型。
- 瞬时故障按 `maxStepAttempts` 有限重试。内容检查按 `maxPolicyRepairAttempts`（默认 2，允许 0–5）反馈脱敏原因，修复当前候选；耗尽后停止。
- `DISCARDED` 仅由明确的 `manual_abandon/abandon` 操作产生。需求不明、低价值、重复、不可行、预算、权限和安全策略均保留为待处理原因。
- `ANOMALY/DEGRADED` 只兼容旧记录；处理时保存可验证的原位置并等待恢复。旧废弃记录不再自动冷却入池。

## 持久化与恢复

`task_recovery` 保存所属工作区、任务版本、原因、节点、分段、计划摘要、配置快照、PR/CI/合并/发布引用和当时尝试计数。状态为 OPEN → RESUMING → RESOLVED；点击恢复只进入 RESUMING，实际步骤通过后才解决。

`task_step_checkpoint` 在开发写入前保存通过检查的候选补丁，提交后保存原始分支头与提交 SHA。进程重启或提交后开 PR 失败时重用原候选及外部操作标识，已有提交不重复创建。模型计费尝试与外部副作用标识分别计算。

恢复必须通过任务版本检查、工作区与角色权限、预算/保护开关检查、PR 分支头核对，以及旧执行者和外部操作终态检查。`DISPATCHING/OUTCOME_UNKNOWN` 不能启动第二个执行；应先通过现有工具操作核对及停止确认流程处理。服务重启不能推断旧执行已终止。

普通恢复保留计划、分段、已完成产物、历史失败与花费，不自动升级流程配置或重新规划。CI 配置修复只更新相关前提、核对分支并重新测试。明确调整开发/规划时增加方案代次，只使相关节点及其依赖结果失效。schema=3 继续使用已接受的计划和固定输入；策略、输入、审批失效时必须先建立或接受适当修订，不能静默换路。

### 手动恢复质量返修

v1/v2 停在 QA 或验收节点、原因为 `same_failure` / `rework_exhausted` 时，明确恢复会补充一轮有限返修额度。`context.reworkQuota` 保存轮次、QA 计数基线、当前失败评审节点的计数基线和待派发返修位置；累计 `loopCount`、`rejectCount`、`nodeLoops` 和历史证据不清零。旧上下文缺少该字段时按零基线读取，无需批量迁移或自动恢复。

- 本轮用量按累计计数减基线判断。额度沿用任务的有效节点配置；恢复评审返修同时补充 QA 额度，其它评审节点的基线保持不变。
- 恢复先完成版本、预算、权限、分支头及旧执行终态校验，再在同一事务中保存新基线、恢复代次和调度状态。失败不改变额度；并发、重复请求只成功一次。`TASK_RESUMED.reworkReset` 记录原因、前后基线、配置额度和累计计数。
- 下一步消费持久化的待返修标记，携带已保存失败报告回开发。此动作占用一次返修额度，不重新查询旧报告、不增加检查运行数和连续失败数。新检查结果才参与连续同错判定；新一轮再次耗尽仍停止等待人工处理。
- QA 和评审退回开发都建立新执行轮次，使用新的候选检查点；保留原计划、PR 分支和已提交分段，整体返修一次。未改代码时仍沿用现有 CI 重跑及旧 run 排除规则。
- 普通暂停使用当前进度，不回退到历史恢复点，也不补充返修额度。执行异常只重置步骤重试；预算、权限、环境、发布限制和 schema=3 不进入此返修额度逻辑。

详情页恢复、对话恢复和阻塞后的带提示重试遵循同一规则，界面展示本轮额度、历史累计计数及恢复后的行为。派发返修时恢复记录仍为 RESUMING，实际执行完成后才解决。

### 返修基线与检查证据

远程开发首次执行时解析固定的仓库提交；已有 PR 的返修和分段续写固定使用当前 PR 的 headSha，不得重新从主干开始。运行器返回实际 baseSha，后端在接收结果和写入 Git 提交时分别核对基线；基线缺失、分支变化或无法核验时停止，不回退到另一种编码方式后应用旧补丁。分支创建记录仅保证创建幂等，不能替代当前分支头的查询。旧的未提交远程候选如果没有基线证明，需要重新生成，不能直接覆盖已有修改。

失败 job 的完整脱敏日志保存在 ci_log，仅清理终端颜色、时间戳和运行器目录前缀。test_report 增加结构化失败报告（检查、用例、文件、行号、错误和完整详情）及 logComplete。返修提示使用完整失败日志，不再按前 30 行或 1800／3000／5000 字符截掉错误；仍受模型容量和任务预算约束。日志无法读取或为空时保留现场并以 evidence_missing 停止，不进行缺少依据的自动返修。历史已截断日志无法从旧摘要还原，需要从 CI 重新取得。

编码完成表示候选补丁已提交、等待测试，不能据此判定修复成功。配置的 CI 工作流必须有非空检查结果，所有 job 均成功；跳过、中性或未完成的 job 不能证明检查通过（可选 job 应放在单独的非门禁工作流）。QA 的附加检查也必须满足；test_report.passed 表示 CI 与附加检查的合并结果。进入验收前再次核对 PR 头，旧提交上的通过结果不能用于新提交的验收。

## 无进展超时

传统 v1/v2 巡查按最近有效进展计算停滞时间：SPEC、DESIGN 为 4 小时，DEV 为 8 小时，QA 为 2 小时。`task.context.lastProgressAt` 在阶段／节点推进、成功提交分段以及通过全部检查的恢复动作中刷新；普通等待、CI 轮询、失败重试和丢弃旧信号均不刷新。`status_changed_at` 保留阶段迁移时间，不因恢复或同阶段分段提交而重写。

旧任务没有 `lastProgressAt` 时，使用当前阶段开始时间与本阶段内最近一次 `TASK_RESUMED`／`SPLIT_PART_COMMITTED` 成功事件确定基准。仅采纳匹配当前节点的恢复事件、已反映在当前分段位置中的提交事件，不改写原事件或批量启动任务。

巡查只为可调度的等待任务生成超时信号，继续排除暂停、已停止以及受项目／保护开关限制的任务。信号绑定观察到的任务版本、节点、进展时间和恢复代次；发送前核对任务版本，消费前重新核对节点、进展、代次及超时条件。成功恢复会移除之前的超时信号，保留其它异常信号；恢复检查失败则保持原计时和信号。重复巡查不会累积相同的待处理超时。

文案使用“连续 N 小时没有有效进展”并提供最近进展时间，避免把阶段驻留时间误称为心跳缺失。schema=3 继续使用其执行租约和节点心跳巡查，传统超时巡查不接管它。

## 操作

- `GET /api/tasks/{id}/recovery`：恢复位置与原因。
- `POST /api/tasks/{id}/resume` 或 `/restore`，请求 `{ "expectedVersion": <当前版本> }`：从保存的位置继续；历史结束任务恢复需要管理权限。兼容旧的空请求恢复入口。
- 对话中的“恢复执行/恢复原进度/带提示重试”使用同一服务；操作确认绑定精确任务版本。
- 对话中的“改方向”明确选择开发或规划；schema=3 在流程编辑器建立修订。
- “从头重新开始”保持独立入口，明确确认后回需求池，新建分支代次并清理本轮产物引用；历史证据与成本保留。

历史恢复优先使用已保存检查点，否则使用原阶段、事件和节点执行记录重建。缺少足够证据、分支已变化或计划摘要不匹配时返回具体原因，不猜测恢复位置。不会批量自动启动历史任务。旧 Issue 被关闭时，明确恢复后尝试重新打开；同步失败保留审计记录。

## 内容策略

路径、内容分别产生结构化违规类型。已知密钥检测始终检查完整文本；JS/TS 内容检查不执行源码、不读取任何环境值。

普通具名配置（NODE_ENV、PORT、HOSTNAME，以及不含敏感名称的 NEXT_PUBLIC_*）允许使用。其它变量需在项目配置声明变量名和服务端入口，例如：

```json
{
  "allowedEnvNames": ["NEWS_API_TOKEN"],
  "serverEnvPaths": ["src/server/"]
}
```

任务快照与当前项目配置取更严格的范围。声明新增权限后，原任务需要明确核对并升级项目配置或重新规划；不能靠旧快照扩大权限。禁止整份环境枚举、动态变量名、客户端敏感读取、疑似敏感配置进入日志/响应/外联，以及进程执行。注释和普通字符串中的 API 名称不会单独触发。词法检查为保守启发式，不等同于数据流安全证明，仍受提交/合并检查与运行环境限制。

## 验证

回归覆盖分段保留与继续、历史任务恢复、未知错误、自愈耗尽、版本冲突、并发恢复、提交后失败重用检查点、未知外部结果阻止重复执行、schema=3 原计划续跑、策略与审批有效性、内容误报，以及节点看板和恢复文案。

无进展回归还覆盖：旧 DEV 阶段恢复后连续完成第 13／14 段、长任务每段提交刷新计时、普通轮询和失败重试不刷新、真正超时只产生一个待处理信号、旧进展／旧恢复代次／过期巡查快照失效、旧数据事件回退，以及恢复失败与其它异常信号的保留。

返修回归覆盖：QA 次数耗尽与连续同错后真实调用编码助手并提交、新一轮再次有界停止、代码审查和页面验收恢复后重新执行、其它节点额度保留、暂停不回旧检查点、校验失败不补额度、并发与对话入口幂等，以及 schema=3 原计划与输入保留。

基线与日志回归还覆盖：远程返修和分段续写使用 PR 提交、结果基线缺失或错误不回退、执行期间分支变化、写入前基线变化、分支创建幂等记录不冻结头提交、真实临时 Git 仓库保留前轮修改、40／60 个失败及长 diff 完整传递、TS 类型错误和 Vitest 文件位置、ANSI 清理、日志过期停止，以及 CI 与附加检查合并后才允许进入验收。
