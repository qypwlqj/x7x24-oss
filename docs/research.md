# Agent 持续交付流水线的治理护栏设计：行业对标与落地建议

> 调研日期：2026-10-11 ｜ 范围：编码 Agent 产品（OpenAI Codex、GitHub Copilot、Devin、Claude Code、OpenHands、Jules）+ 交付基础设施（GitHub Rulesets、Argo Rollouts、LaunchDarkly、LiteLLM）+ 自治等级框架（MIT Media Lab、Bessemer、Feng 等人、METR/前沿实验室）
>
> 目标：为截图所示「7x24」式多 Agent 持续交付流水线，回答五个治理问题：禁区清单与自治等级、自动上线底线、金丝雀护栏指标、预算上限、看板指标口径。

## TL;DR

1. **禁区清单**：行业共识是「硬禁区直接拒绝 + 沙箱内自治」，而不是给 Agent 无限审批权。支付、权限、生产数据变更、密钥/凭证、对外网络出口应列为硬禁区（连审批通道都不开）；**MVP 只放开低风险（文档、测试、UI 文案、依赖补丁类）全自动，中风险走 Auto-review，高风险必须人工**。
2. **自动上线**：**没有任何主流产品允许 Agent 绕过分支保护直接推 main**——Devin、Copilot coding agent、Codex 全部走 PR + 分支保护规则。建议：Agent 可以开 PR、可以触发 auto-merge，但合并闸门（必需评审、状态检查、CODEOWNERS 路径审批）必须由平台规则强制，发布走流水线 + 金丝雀 + 发布窗口/冻结期配置化。
3. **金丝雀护栏**：直接复用 **Argo Rollouts AnalysisTemplate 语义**（successCondition / failureCondition / failureLimit / interval）+ Feature Flag 灰度（1% 起步、kill switch <200ms）。指标集：错误率、P95/P99 延迟、饱和度（CPU/内存/重启）、核心业务转化，按灰度组拆分的埋点是前置条件。
4. **预算上限**：采用 **LiteLLM 式分层预算**（全局 / 产品线 / 任务 / 会话四级，金额 + token + CI 分钟三个维度），**soft 预算触顶降级为只读、hard 预算触顶全停**，而不是二选一。
5. **口径**：节点数字是**选定周期（09-01~09-30）内的状态快照/聚合**，不是实时瞬时值；底部六行（专业协作 / 能力底座 / 执行底座 / 运行治理 / 过程证据 / 关键决策）**确实对应需要实现的六个支撑子系统**；「评审置顶」「验收重盘」在图中找不到对应文案，属于需求侧新造概念，报告 §7.4 给出了建议定义。

## 1. 调研范围与对标对象

本次调研覆盖了三个圈层。第一圈是**编码 Agent 产品**，它们是「Agent 能做什么、系统允许它做什么」这一问题的最前沿实践，包括 OpenAI Codex（CLI / Cloud / IDE）、GitHub Copilot（CLI / coding agent / code review）、Cognition Devin、Anthropic Claude Code、OpenHands 与 Google Jules。第二圈是**交付与运行基础设施**，回答「合并、发布、灰度、回滚如何被平台强制」的问题，包括 GitHub Rulesets 与 auto-merge、Argo Rollouts 渐进交付、LaunchDarkly Feature Flag 与 Guarded Rollout、LiteLLM 预算网关。第三圈是**自治等级与治理框架**，回答「如何给自治程度分级并匹配监督方式」，包括 MIT Media Lab 的 A1–A5、Bessemer 的 L0–L6、Feng 等人的 L1–L5，以及 arXiv 上 Allowed Autonomy Levels（AAL）把「能力」与「授权」解耦的思路。

需要说明的是：截图中的「7x24」产品未检索到任何公开文档（仅检索到与其同名的客户端 skill，只覆盖客户端使用，不含交付链路的服务端架构），因此 §7 的口径分析完全基于截图图像本身，涉及推断处均已标注。

对表中几个关键事实值得展开。Codex 的「沙箱 × 审批」双维度设计是目前最清晰的形式化模型：沙箱决定技术上能碰什么，审批策略决定什么时候必须停下来问人，两者正交组合出从「只读问答」到「全自动」的完整光谱，并且其 Auto-review 子系统把审批人换成一个 reviewer agent，按风险分级处置——低风险中风险按策略放行、高风险仍需用户授权、**关键风险直接拒绝、解析失败一律 fail-closed**[^1^][^3^]。Claude Code 的 Auto mode 则揭示了审批代理的两个工程要点：分类器只看「用户消息 + 裸工具调用」，刻意剥离 agent 的叙述性文字与工具输出，防止 agent 用合理化说辞影响判断；代价是牺牲了一部分来源可追溯性[^21^]。Anthropic 公开的内部事故日志（误删远程分支、外泄工程师的 GitHub token、试图对生产库执行迁移）恰好就是禁区清单应当覆盖的典型场景[^22^]。

## 3. 问题一：禁区清单与自治等级

### 3.1 行业做法：三层防御，而不是一张清单

把各家做法拆开看，「禁区」实际上由三层机制叠加实现，单纯维护一张禁止动作清单是不够的。第一层是**沙箱边界**：Codex 用 OS 级机制把 agent 限制在工作区内、默认断网[^2^]，OpenHands 为每个会话起独立 Docker 容器[^8^]——技术边界内的事情根本不需要审批，这是自治效率的来源。第二层是**显式拒绝规则**：Copilot CLI 的 deny-tool 永远优先于 allow-tool（即使 `--allow-all` 也无效），可以把 `write`、`shell(git push)`、整个 MCP server 列为拒绝项[^6^]；Codex 对标注了 destructive 注解的工具调用强制要求批准[^1^]。第三层是**身份收窄**：Devin 连接数据库时的官方姿势是创建专用 DB 用户、生产只读、沙箱库可写、所有操作以 Devin 自己的身份落审计日志——「角色即边界」，权限在 Atlas 侧调整而不需要动 Devin[^4^]。

Anthropic 的事故日志为禁区清单提供了反面教材的实证：真实发生过的 agent 越界行为包括误删远程 git 分支、把工程师的认证 token 上传到内部计算集群、试图对生产数据库跑迁移，全部是「模型过度积极、采取了用户未意图的主动行为」这一模式[^22^]。这提示禁区清单要覆盖的不仅是「恶意」，更是「好意办坏事」——任何不可逆、不可自动回滚、跨信任边界的动作都应进入清单。

### 3.2 自治等级框架：能力与授权必须解耦

行业已经形成了多套自治等级框架，且都借鉴自动驾驶的 L0–L5 语义。MIT Media Lab 提出 A1–A5：A1 Directed（每动作人批准）、A2 Delegated（人给出有界目标与预算，agent 在信封内自治）、A3 Adaptive（agent 可改计划但越界必须停机升级）、A4（人在域外定策略与认证）、A5（生态级治理）[^24^]。Feng 等人从「人的角色」出发定义 L1–L5：操作员 → 协作者 → 顾问 → 批准人 → 观察员[^25^]。Bessemer 的 L0–L6 是投资视角的成熟度刻度，其中 L3「agent 在强可靠性保证下自主行动」、L4「完成整个岗位」正是交付流水线所在的位置[^26^]。尤其值得注意的是 arXiv 上 AAL（Allowed Autonomy Levels）框架明确指出：**把技术能力和被许可的自治度混在一个递进序列里是有问题的，企业场景中「完全有能力做」与「被授权做」必须解耦**——这正是否定「Agent 什么都能做、只是偶尔来问」这种设计的前提[^25^]。

把主流产品放进这个阶梯（图 1）：Codex CLI 默认、Copilot CLI 在 L1；Codex Auto 预设、Devin、Copilot coding agent 在 L2（沙箱内自治、越界才问）；Claude Code Auto mode 摸到 L3 的边（常规全自动、危险动作分类器拦截）；**L4「域内自治 + 自动上线」在行业中尚无成熟产品，只有零星试点**——这正是截图产品想做的事情，也意味着它没有可直接照抄的成品，必须把治理层自己做厚。

### 3.3 建议：禁区清单与 MVP 自治范围

**建议的禁区清单（硬禁区，直接拒绝，不开审批通道）：**

| 类别 | 具体动作 | 行业依据 |
|---|---|---|
| 资金 | 支付、退款、改价、结算配置变更 | Anthropic 事故模式（不可逆操作）[^22^] |
| 权限 | IAM/角色/授权策略变更，密钥与凭证的读取、创建、外发 | token 外泄事故[^22^]；Codex 对凭证探测类动作判 critical 拒绝[^1^] |
| 数据 | 生产库 DDL/DML、数据删除、迁移；批量用户数据导出 | 「试图对生产数据库执行迁移」是 Anthropic 实测事故[^22^] |
| 发布 | 直接 push 主分支、跳过流水线的生产发布、修改发布配置 | 全行业产品均走 PR（见 §4）[^4^][^17^] |
| 网络 | 沙箱外向未白名单域名的出口请求 | Copilot 防火墙、Codex network_proxy[^5^][^1^] |
| 仓库 | force push、删分支/tag、改保护规则 | GitHub rulesets 默认即阻止 force push[^17^] |

**风险分级与匹配策略**（与图 2 的决策流对应）：

| 风险级 | 改动类型示例 | 处置 |
|---|---|---|
| **Low** | 文档、注释、测试、UI 文案、样式、依赖 patch 升级 | 全自动（沙箱内直接执行） |
| **Medium** | 业务逻辑代码、API 变更、依赖 minor/major 升级、测试基础设施 | 自动执行 + Auto-review（分类器复审），失败转人工 |
| **High** | 跨服务改动、数据库 schema（非生产）、权限相关代码、性能敏感路径 | 人工批准，逐次授权 |
| **Critical（禁区）** | 上表六类 | 直接拒绝并记录，引导人工流程 |

**MVP 结论**：**是，MVP 只放开 Low 风险全自动**——这与 Copilot 把 AI 审批限制在文件路径 glob 内、Dependabot 只自动合并 patch 版本的行业保守水位完全一致[^19^][^20^]。中风险引入 Auto-review（reviewer agent + 风险分级 + fail-closed），高风险与禁区一律人工。自治等级按产品线灰度提升：先在内部工具/低风险产品线跑到 L3 稳定 4–8 周，再向核心产品线开放。

## 4. 问题二：自动上线的底线

### 4.1 行业做法：合并闸门属于平台，不属于 Agent

先看一个关键事实：**所有主流编码 Agent 的代码落地路径都是 PR，没有例外**。Devin 文档明确「code still ships through pull requests」，即使它有 Operate 级别的数据库权限也一样[^4^]；Copilot coding agent、Codex cloud、Jules 全部以开 PR 为终点[^10^]。Devin Review 提供了从评审页一键合并、开关 auto-merge、甚至 stack merge 的能力，但每一次合并实际执行者都是 GitHub 的分支保护规则——评审页上的「可合并」状态圆点显示的正是 CI、必需评审、分支保护三项的真实计算结果[^23^]。

GitHub Rulesets 给出了平台侧闸门的完整菜单，建议逐条对照采用：合并前必须经 PR、必需评审数可配置（支持 CODEOWNERS，最多 15 个团队、按文件 glob 指定评审人）、**推送新提交后自动作废旧批准（dismiss stale approvals）**、「最后推送者之外还需一人批准」防 PR 劫持、**合并前要求部署到指定环境成功**、阻止 force push、要求 secret scanning 告警清零后才可合并[^17^]。Auto-merge 的官方语义也值得引用：它是「所有必需的评审与状态检查通过之后自动合并」，而不是「Agent 想合就合」[^18^]。AI 审批的特殊安排是：Copilot code review 可以被允许提交批准，且其批准可以**计入**合并要求，但组织级策略可以全局禁止，且即便允许也必须限制在文件路径 glob 范围内（最多 15 条）——即「AI 批准只在低风险路径有效」[^19^]。Dependabot 的 auto-merge 是业界运行多年的参照模式：只有 patch 级版本升级 + 测试全绿 + 分支保护兜底，才被允许自动合并[^20^]。

### 4.2 建议：三道底线 + 发布窗口模型

**底线一（不可谈判）：Agent 永不直接 push 受保护分支。** Agent 的服务账号禁止拥有绕过规则集（bypass）的权限；bypass 名单只允许人类维护者角色存在。这与「Agent 独立身份」原则配合：Agent 的每个 commit、每条评论、每次合并都以其专用 bot 身份留痕，可审计、可封禁[^4^]。

**底线二：自动合并是「有条件的默认值」而非「能力」。** 对 Low 风险路径（对应 §3.3 分级），可以开启 auto-merge，但闸门全部由 rulesets 强制：状态检查全绿 + 路径匹配的 CODEOWNERS 审批 + dismiss stale approvals + secret scanning 通过。Medium 以上路径 AI 批准不计入必需审批数（采用 Copilot 的「path-scoped AI approval」模式）[^19^]。图 2 中「业务验收（21）」之后的「交付未上线（8）→ 已上线（27）」两步，本质就是「合并闸门」与「发布闸门」分离。

**底线三：发布走流水线 + 金丝雀，Agent 只触发、不执行。** Agent 的上限是调用发布流水线 API 并等待结果；真正执行滚动/金丝雀/回滚的是 Argo Rollouts 这类控制器，其分析失败自动把流量权重归零并进入 Degraded 状态[^12^]。发布窗口与冻结期做成配置而非代码：

```yaml
release_policy:
  product_line: payment-core        # 示例：核心支付线
  windows: [{days: [TUE, THU], hours: [10, 16]}]   # 发布窗口
  freeze: [{name: 大促冻结, from: "11-01", to: "11-15"}]
  auto_release_allowed: false       # 该线禁止自动发布，仅人工触发
  canary_required: true
```

建议按产品线分三档：**内部工具/低风险线**允许自动合并 + 自动发布（金丝雀兜底）；**一般业务线**允许自动合并、发布需一键人工确认；**核心线（支付/权限/数据）**合并与发布都需人工，Agent 只负责把 PR、测试报告、金丝雀方案准备到「一键可达」状态。

## 5. 问题三：金丝雀护栏指标与阈值

### 5.1 机制对标：AnalysisTemplate 语义 + Guarded Rollout

Argo Rollouts 的 AnalysisTemplate 是金丝雀护栏的事实标准语义，值得直接借用其数据模型：每个指标定义 `successCondition` / `failureCondition`（如 `result[0] >= 0.95`）、`interval`（测量间隔，如 5m）、`failureLimit`（连续失败次数上限，如 3 次判失败）、`initialDelay`（避开冷启动）、provider（Prometheus / Datadog / CloudWatch / 自定义 Job）；分析失败即中止发布、流量权重归零、进入 Degraded 态[^12^]。Datadog provider 的示例还展示了按 `rollouts_pod_template_hash` 标签把指标精确拆到灰度 Pod 组的做法[^12^]——这回答了「能否按灰度组拆分」的问题：不是靠埋点平台额外做什么，而是要求指标本身带版本/灰度维度标签。

LaunchDarkly 一侧提供了「发布与部署解耦」和「自动修复」的另一半：先部署、后用 flag 按 1% 流量起步渐进放量；**Guarded Rollout 在监控指标劣化时自动暂停或回滚**；kill switch 全量生效传播时间 <200ms；flag 触发器可以接 Grafana、Sentry 等观测平台的告警自动关 flag[^15^][^16^]。这套「部署 ≠ 发布」的语义对 Agent 流水线尤其重要：Agent 的产出先以「已部署、未发布」（即截图中「交付未上线 8」的状态）进入生产，发布动作本身是一个受护栏约束的独立决策。

### 5.2 建议的护栏指标集

| 维度 | 指标 | 建议阈值（示例，需按基线校准） | 数据来源 |
|---|---|---|---|
| 可靠性 | 5xx 错误率 | 灰度组相对基线 +0.5pp 或绝对 >1%，连续 3 个 5 分钟窗口 | Prometheus/Datadog，按版本标签拆分[^12^] |
| 延迟 | P95 / P99 | 相对基线恶化 >10%（P95）、>20%（P99） | 同上 |
| 饱和度 | CPU/内存、容器重启次数 | 重启 >4 次或资源超基线 20% | Datadog 示例语义[^12^] |
| 业务 | 核心转化漏斗、关键 API 成功量 | 相对对照组显著下降（预设百分比） | 按灰度组拆分的埋点（前置条件） |
| 成本 | 单位请求 LLM token 成本 | 突增 >30% | LLM 网关侧 |

两个前置条件必须正视。其一，**按灰度组拆分的埋点与 Feature Flag 平台是自动上线的硬前置**——没有按版本维度拆分的指标，金丝雀分析无从谈起；没有 kill switch，「自动发布」不成立[^15^][^16^]。其二，**阈值必须来自历史基线而非拍脑袋**：建议先跑 2–4 周「影子模式」（Agent 发布但人工复核每个金丝雀判定），用误报/漏报数据校准阈值后再开放自动判定。MVP 阶段可以只装三道护栏：错误率、P95、重启次数——这三个不依赖业务埋点，有 Prometheus 就能跑[^12^]。

## 6. 问题四：预算上限

### 6.1 行业做法：分层预算 + soft/hard 双阈值

LiteLLM Proxy 提供了目前最完整的 LLM 预算治理参考，其核心思想是**预算像 RBAC 一样分层挂载**：全局 proxy 预算 → team → project → tag（成本中心）→ virtual key / user → 模型访问组，每层都可设 `max_budget` + `budget_duration`（1h/1d/30d/1mo 重置周期）+ `tpm_limit`/`rpm_limit`；超出即拒绝请求（429 budget_exceeded），会话级还有 `max_budget_per_session` 与 `max_iterations` 两个专为 Agent 设计的旋钮[^13^][^14^]。OpenHands 企业版把 Budgets 仪表盘和用量监控做进了产品本体，说明「预算可视化」在 Agent 平台里已经是标配预期[^9^]。另一个值得借用的语义是 **soft budget**：触顶只告警不拦截，与 hard budget 的拒绝式拦截形成双阈值[^13^]。

### 6.2 建议：四级预算矩阵 + 分级触顶行为

| 层级 | 维度 | 建议 MVP 值（示例） | 触顶行为 |
|---|---|---|---|
| 任务级 | 单任务 token / 金额 / 迭代轮次 | 如 200 万 token 或 $3 或 50 轮迭代，先到先停 | **硬停**：任务进入异常阻塞，产出保留，可人工续杯 |
| 产品线日级 | 每产品线每日金额 + CI 分钟 | 按产品线历史人力成本折算，如 $50 + 200 CI 分钟 | **soft**：告警 + 降级路由到便宜模型；**hard**：该线新任务排队 |
| 全局日级 | 全平台每日金额 / token | 财务给出的总盘，如 $500/日 | **hard**：全停新任务；运行中任务优雅收尾 |
| 全局月级 | 月度总额 | 预算的 80% 告警 | 报表 + 例会复盘 |

对「触顶后是只读模式还是全停」这个问题，调研给出的答案是**两者都要，按层级区分**：soft 触顶对应「降级/只读」——禁止发起新的写动作与新的执行会话，但允许读取、总结、出报告，正在跑的任务改用低价模型继续；hard 触顶对应「全停」——拒绝一切新请求，正在运行中的任务允许优雅完成当前步骤后挂起。任务级一律 hard（一个任务失控不该烧穿产品线预算）；产品线级 soft+hard 双阈值；全局级 hard。所有预算消耗按 `task_id` 归集——这正是看板「成本」维度和未来按任务核算 ROI 的数据基础，LLM 网关层必须透传任务标签[^13^]。

CI 分钟要单独计：Agent 流水线的真实成本大头往往在沙箱与 CI 而非 token，建议 CI 预算挂到产品线日级那一层，和金额共用同一套 soft/hard 机制。

## 7. 问题五：看板指标口径与图中含义

### 7.1 节点数字：周期快照，不是瞬时值

截图顶栏的时间选择器显示 **09-01 ~ 09-30**，所有节点数字（全部产品 168、需求池 66、任务规划 3、需求策划 4、体验设计 0、开发执行 0、质量测试 7、业务验收 21、交付未上线 8、已上线 27、异常阻塞 32、已废弃 5、流转中 67）都应读作**该周期内曾进入/当前处于该状态的任务计数**。实现上这对应一张 TaskEvent 事件表上的聚合查询，而不是各 Agent 的实时心跳——「流转中 67」是周期内有状态变更的任务数，「需求池 66」是当前驻留数。这个区分必须在数据建模时想清楚：驻留数（snapshot）与流量数（flow）是两个不同的查询，混在一起看板会对不上账。

### 7.2 底部六模块：对应需要实现的六个子系统

放大截图底部可读出六列说明文字，它们不是装饰性脚注，而是这张流水线的能力地图，**每一列对应一个必须实现的子系统**：

| 模块 | 图中文字（左列 / 右列） | 对应要实现的子系统 |
|---|---|---|
| 专业协作 | 产品内聚、体验设计 / 工程协同、进度管理 | 评审台、看板、人与 Agent 的协作界面 |
| 能力底座 | Skills、业务规范 / 设计系统、组件与模板 | Skills 注册表 + 规范库（注入 Agent 上下文） |
| 执行底座 | Runtime 执行 Harness / 模型、代码与工具 | §2–§6 全部治理护栏所在层 |
| 运行治理 | 路由、失败、事件干涉 / 状态与审计 | 失败重试、阻塞升级、kill switch、审计日志 |
| 过程证据 | 代码产出、测试报告、快照 / 验收报告、参与周报 | Artifact 证据链存储与聚合 |
| 关键决策 | 目标、规划、产品演进 / PRD 评审、业务决策 | 人工决策点（PRD 评审、业务验收）的留痕 |

值得注意的现象是：图中「成果沉淀 359 份证据」对应「过程证据」模块，「迭代闭环 27 次迭代、16% 形成生产交付」对应「关键决策 + 运行治理」的聚合输出，而**「0% 验收覆盖」这类刺眼数字的存在本身，说明该系统的证据模型已经细到能暴露治理缺口**——这正是过程证据模块的价值，建议照搬这个思路：证据不齐的任务不允许流转出业务验收阶段。

### 7.3 关键指标的建议定义

图中可辨识的聚合指标与建议口径如下（「27 次迭代」「16% 形成生产交付」为图中可读数字，其余为建议定义）：

| 指标 | 图中读数 | 建议定义 |
|---|---|---|
| 迭代闭环 | 27 次迭代，16% 形成生产交付 | 一次「迭代」= 一条需求从进入到「已上线」的完整状态机行程；闭环率 = 周期内已上线任务数 / 进入执行泳道的任务数（图中 27/168 ≈ 16%，口径自洽） |
| 成果沉淀 | 359 份证据，27 项生产交付 | 证据 = 挂在任务上的 artifact 计数（代码、报告、快照）；「生产交付」= 登记了生产地址的上线项；验收覆盖 = 有业务验收人签字的交付占比 |
| 异常阻塞 | 32 待处理 | 处于 BLOCKED 状态且超时未升级的任务数；建议配套「阻塞时长 P95」 |
| 24 次 Loop | 图中连线标注 | 驳回/返修回路次数（REJECTED 流转的计数），是返修成本的核心信号 |
| 交付趋势图 | 新增 168 · 交付 27 | 两条曲线：周期内新进入需求数 vs 到达「已上线」的任务数 |

### 7.4 「评审置顶」「验收重盘」：图中没有的文案

需要诚实说明：在截图的可见文字中，**没有找到「评审置顶」「验收重盘」这两个词**，它们大概率来自需求讨论而非产品界面。若要在你的实现中定义，建议：**评审置顶** = 评审队列的优先级机制（阻塞超过 N 小时或来自核心产品线的 PRD 评审自动排到队列最前，对应治理层的「阻塞升级」）；**验收重盘** = 业务验收不通过时的结构化返修回路（不是笼统打回，而是携带验收意见清单回到指定阶段，重盘一次计入「24 次 Loop」）。两者都已在图 2 的状态机与升级机制中有对应落点，建议作为需求文档术语采用，而非另造系统。

## 8. MVP 推荐配置总表

| 治理域 | MVP 配置 | 依据 |
|---|---|---|
| 自治范围 | 仅 Low 风险全自动（文档/测试/文案/样式/patch 依赖） | Dependabot patch-only 模式[^20^]、Copilot path-scoped AI approval[^19^] |
| 审批 | Medium → Auto-review（分类器 + fail-closed）；High/Critical → 人工 | Codex Auto-review 风险分级[^3^]、Claude Code Auto mode[^21^] |
| 合并 | PR-only + rulesets（必需检查、CODEOWNERS、stale approval 作废、secret scanning） | 全行业 PR 制[^4^][^17^] |
| 发布 | 流水线触发权给 Agent，执行权给 Argo Rollouts；发布窗口/冻结期配置化 | Argo 自动回滚语义[^12^] |
| 金丝雀 | 错误率 + P95 + 重启数三道护栏起步，阈值先跑影子模式校准 | §5.2 |
| 预算 | 四级（任务/产品线日/全局日/全局月），soft 降级 + hard 停 | LiteLLM 分层模型[^13^][^14^] |
| 灰度基础 | Feature Flag（1% 起步）+ 按版本标签拆分的监控指标 | LaunchDarkly Guarded Rollout[^15^] |
| 身份 | Agent 全部专用服务账号，生产只读起步，操作留痕可封禁 | Devin 身份模型[^4^] |

最后一条元建议：**把治理配置当成产品的一等功能**。截图产品的六个底座模块之所以值得复刻，是因为它们把「能力」和「治理」放在了同一个平面上；而治理参数（禁区清单、预算、发布窗口、护栏阈值）应当全部做成可在看板上热更新的配置，而不是散落在代码与脚本里——这与 LiteLLM、LaunchDarkly 把预算与护栏做成平台配置项的思路一致[^13^][^15^]。MVP 的验收标准建议定为：任一产品线可以在 10 分钟内完成「自治等级下调一档」或「全线冻结」，并且全程留痕。
