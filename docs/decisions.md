# 自治边界决策记录（对应方案 §8 的 5 个开放问题）

> 2026-10-28 更新：执行失败、策略拒绝、预算或自动处理耗尽均停在原节点并保留恢复能力。任务终止由人明确操作。下文的自动废弃、D3 终止及冷却重新入池描述为历史决策，最新规则见 [可恢复交付流程](design/recoverable-workflow.md)。

> 依据：`docs/research.md`（行业对标调研）。**统一改写原则**：用户明确要求「全部由 agent 自动化执行，不需要等人决定」，因此调研中所有「High / Critical 转人工」的建议，在本项目里统一改写为：
>
> - **禁区动作（Critical）= 系统直接拒绝并记录**：不开审批通道、不等人。任务以 `forbidden_scope` 废弃（不可重新入池），工具层动作抛 `PolicyDenied` 并写 `ACTION_DENIED` 审计。
> - **High 风险 = 由独立评审 agent 委员会 + 更严格阈值自动裁决**；失败则自动降级（换方案 → 缩小范围 → 自动废弃）。
> - **kill switch 只是系统保护开关**（READ_ONLY / FREEZE_RELEASE / HALT），不参与任何业务决策；自动触发、条件消除后自动解除。
> - 凡调研写「可人工续杯 / 人工触发 / 一键人工确认」的地方，一律换成「自动续杯（降级阶梯追加预算）/ 更严的自动护栏 / 更低的自治等级」。

所有数值都是 `docs` 里可热更新的默认值（`GET/PUT /api/config`，看板「预算与治理」页），落点见 `apps/server/src/config.ts`。

## 项目架构更新（2026-10-11）

以下以 [产品线、项目与交付任务](project-architecture.md) 为最新实现口径：产品线下有多个项目，仓库和技术上下文属于项目；任务归属项目并在节点之间流转。预算增加项目维度，项目和产品线硬限额触顶后暂停后续步骤，额度恢复后继续；新建产品线仍默认 L1。阶段驻留按 current_stage 聚合，异常视图另行展示，同一异常任务不能重复计入任务总量。发布窗口目前继承全局配置。

## 决定 1：禁区清单与自治等级

**问题**：哪些模块或改动类型禁止自动执行？MVP 是否只放开 low 风险？

**决定**

1. **禁区（六类，硬禁区）**：资金（支付/退款/改价/结算）、权限（IAM/授权策略/密钥凭证的读取创建外发）、生产数据（生产库 DDL/DML、删除、迁移、批量导出）、发布（直接 push 主分支、跳过流水线、改发布配置）、网络（沙箱外向非白名单域名出口）、仓库（force push、删分支/tag、改保护规则）。另外**治理文件**（`.github/`、`CODEOWNERS`、验收用例目录、扫描配置、`deploy/`）禁止被 agent 改动。
2. **处置**：命中即**系统直接拒绝并记录**——需求阶段（分诊/PRD 硬规则/规划/PR 三个时点各判一次，取最高）以 `forbidden_scope` 废弃；工具层动作在 `PolicyGate`（`risk.ts: evaluateAction`）直接拒绝，**deny 优先**，不存在审批入口。
3. **风险分级 → 自治等级**：`low`→L1 起，`mid`→L2 起，`high`→L3；超出产品线当前自治等级同样按 `forbidden_scope` 废弃。
   - Low（文案/样式/文档/测试/patch）：全自动。
   - Medium：自动执行 + **Auto-review**（3 个不同模型的评审委员会 + 仲裁，**解析失败一律 fail-closed**）。
   - High：同样全自动，但 PRD 通过分 +0.10、验收分 +0.05、金丝雀阈值 ×0.5 且 `failureLimit=0`、最短观测时间更长；失败自动降级/缩范围/废弃。
4. **MVP 范围**：新产品线默认 **L1（只放开 low）**。自治等级**自动收紧**（24h 内自动废弃 > 5 或回滚 > 2 → 降一级并暂停入场 12h）；**放宽需连续 30 天达标**（≥5 次上线且 0 回滚）才自动升一级。

**依据**：调研 §3——行业共识是「硬禁区直接拒绝 + 沙箱内自治」（Codex 对 critical 拒绝、Copilot deny 优先于 allow、Anthropic 事故日志覆盖的不可逆动作）；Dependabot 只自动合并 patch、Copilot AI 审批限定路径 glob，说明 MVP 只放 low 是行业保守水位；AAL 框架要求「能力」与「授权」解耦，所以自治等级放在产品线配置而非 agent 能力里。调研里的「High 人工批准」按全自治约束改写为上面第 3 条的委员会 + 严阈值。

## 决定 2：自动上线的底线

**问题**：是否允许 agent 直接合并 main 并发布生产？发布窗口和冻结期是什么？

**决定**

1. **底线一：agent 永不直接 push 受保护分支**。`git.push` 只允许 `agent/*`；`release.direct`/`git.force_push` 属禁区。合并与发布只能经「发布流水线」：先通过 **Release Gate**（CI 绿、SAST/漏洞/密钥扫描、许可证、变更规模 ≤500 行/20 文件、迁移可逆、带 Flag、验收 verdict 齐全、**证据链哈希校验**）再进入灰度。
2. **底线二：自动合并是有条件的默认值**：仅当三层验收（用例 100% + 委员会 ≥0.8 + Release Gate）全部通过才合并；证据不齐一律驳回（呼应调研「证据不齐的任务不允许流转出业务验收」）。
3. **底线三：发布走流水线 + 金丝雀，agent 只触发不执行**（`ToolAdapter.deploy`）。
4. **发布窗口 / 冻结期做成配置**（全局默认 + 产品线覆盖，按 UTC 判定）。默认全天候开放；示例：「核心交易」产品线仅允许周二/周四窗口 + 「大促冻结」冻结期（见 `demo.ts`）。不在窗口内的任务停留在「交付未上线」并写 `RELEASE_WAIT`，窗口开启后自动继续。
5. 调研的三档（内部/一般/核心）改写为**同一套全自动流程、不同严格度**：核心线 = 更低自治等级（默认 L2）+ 受限发布窗口 + 严格金丝雀，而不是「人工触发」。

**依据**：调研 §4——所有主流产品都走 PR + 分支保护，合并闸门属于平台而不属于 agent；GitHub Rulesets / auto-merge 的语义是「必需检查通过后才合并」；Argo Rollouts 把执行权交给控制器。调研建议的「核心线需人工」按全自治约束改写为上面第 5 条。

## 决定 3：金丝雀护栏指标与阈值

**问题**：用哪些指标判定劣化？是否有可按灰度组拆分的埋点和 Feature Flag？

**决定**

1. **采用 Argo AnalysisTemplate 语义**：每个指标 `successCondition` / `failureLimit` / `interval` / `initialDelay` / `count`（`config.canary.metrics`，`canary.ts` 里是纯规则判定，**不使用 LLM**）。
2. **指标集（MVP 即三道护栏 + 绝对错误率）**：
   | 指标 | successCondition | failureLimit | 采样 |
   |---|---|---|---|
   | `error_rate_delta_pp`（相对基线增幅） | `result < 0.5` | 1 | 5m × 3 |
   | `error_rate_abs_pct` | `result < 1` | 1 | 5m × 3 |
   | `p95_regression_pct` | `result < 10` | 1 | 5m × 3 |
   | `restart_count` | `result <= 4` | 0 | 5m × 3 |
3. **灰度档位** 1% → 5% → 25% → 100%，每档最短观测 30 分钟（high 风险 120 分钟）；**high 风险阈值 ×0.5 且 failureLimit=0**。样本不足判 `inconclusive`，不放行。
4. **任一护栏失败 → 自动回滚（目标 ≤5 分钟）**：关 Flag/回退版本（幂等），写回滚证据，任务带事故证据回规划；同任务回滚 2 次进入降级阶梯；上线后 72 小时观测期内同样判定、同样回滚。
5. **前置条件**：指标必须带版本/灰度标签、有 Feature Flag 与 kill switch——这是 `ToolAdapter.deploy` 接口的契约（Mock 实现按灰度组产出指标）。接真实 Prometheus/Datadog + Flag 平台时只需实现该适配器。
6. **「影子模式校准」改写为自动校准**：不等人复核，而是把「验收重盘率」（自动验收通过后又被回滚的比例）作为反馈信号，超阈值时自治等级自动收紧；阈值本身可热更新。

**依据**：调研 §5——Argo 语义是事实标准；LaunchDarkly Guarded Rollout 的「部署≠发布」「按指标自动暂停/回滚」；MVP 只装三道不依赖业务埋点的护栏（错误率、P95、重启数）即可运行。

## 决定 4：预算上限

**问题**：单任务/产品线日/全局日的 token、金额、CI 分钟上限？触顶后只读还是全停？

**决定**（金额 + token + CI 分钟三个维度，**任一维度先到先触发**；全部按 `task_id` 归集到 `budget_ledger`）

| 层级 | 默认值 | soft | hard（自动，无人工） |
|---|---|---|---|
| 任务 | 2,000,000 token / $3 / 60 CI 分钟 / 50 轮 dev 迭代 | 80%：提示规划 agent 收敛范围 | 进入**降级阶梯**：D1 追加原预算 50%（换方案）→ D2 追加 30%（缩小范围）→ D3 以 `budget_exhausted` 自动废弃（取代「人工续杯」） |
| 产品线日 | $50 / 200 CI 分钟 / 40M token | 80%：**降级路由到便宜模型** + 告警 | 该线**新任务排队**（不再入场），在途任务继续走完测试和发布 |
| 全局日 | $500 / 2000 CI 分钟 / 400M token | — | **自动 READ_ONLY kill switch**：停一切写操作，在途优雅收尾；次日或上调预算后**自动解除** |
| 全局月 | $10,000 | 80%：告警（审计 `BUDGET_HIT`） | 100% 同全局 hard |

「只读还是全停」：**两者都要，按层级区分**（soft=降级，hard=停新任务/全局只读），与调研一致。账本写入带幂等键，重放不重复计费。

**依据**：调研 §6——LiteLLM 分层预算（全局/产品线/任务）+ soft/hard 双阈值；Agent 流水线的成本大头常在 CI，所以 CI 分钟与金额共用同一套机制；`max_budget_per_session`/`max_iterations` 对应任务级的迭代轮次。

## 决定 5：看板口径与图中含义

**问题**：节点数字是否为快照？「评审置顶」「验收重盘」「27 次迭代」的确切定义？底部说明行是否对应需要实现的模块？

**决定**

1. **驻留数 vs 流量数必须分开**（调研 §7.1）：
   - **驻留数（resident，节点大数字）**：区间内创建的任务中，**当前**处于该状态的数量（快照）；
   - **流量数（flow，悬停可见）**：区间内创建的任务中，**曾进入**该节点的不同任务数。
   日期范围按任务创建时间过滤，可按产品线筛选。外框 = Watch(需求池+PRD 评审) + Prism(规划…验收+异常/降级) + 交付未上线 + 已上线，**不含已废弃**；异常巡查卡片含 `DEGRADED`。
2. **迭代 / 闭环**：一次「迭代」= 一条需求从进入到「已上线」的完整状态机行程（`iterations` = 流入已上线的任务数）；闭环率 = 当前已上线 / 外框总数。观测 agent 回流产生的新任务另计 `iterate` 边。
3. **Loop 数** = `edge=qa_loop` 的事件数（QA→规划/降级的返修回路）。
4. **评审置顶** = PRD 评审判「需补充」→ 带意见退回需求池并**提升排序**（优先级 +0.1，`review_pin` 边，最多 2 次）。
5. **验收重盘** = 自动验收通过后又被回滚（灰度或观测期）的任务占比（`recheckRate`）——自动裁决质量的核心指标；驳回修改（`reject` 边）是带验收意见清单回规划的结构化返修。
6. **成果沉淀** = 区间内 evidence 条数（WORM + sha256）；「生产交付」= 状态为已上线的任务数。
7. **底部六模块 = 六个子系统，均有落点**：专业协作（看板 + 任务详情/时间线）、能力底座（`agents/` 角色注册表与提示版本 + 可热更新的治理配置；Skills 注册表为后续项）、执行底座（`ToolAdapter` + 沙箱接口 + `LlmProvider`）、运行治理（Patrol 自愈/降级、kill switch、审计哈希链）、过程证据（`EvidenceStore`）、关键决策（`VerdictStore`：PRD 评审与业务验收的**自动裁决留痕**，不是人工决策点）。

**依据**：调研 §7——节点数字是周期快照而非瞬时值，驻留与流量是两个不同查询；底部六列是能力地图；「评审置顶」「验收重盘」在图中无文案，采用调研 §7.4 的建议定义，并按全自治约束落到状态机与 Patrol 上。
