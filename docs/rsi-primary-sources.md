# Agent RSI 一手资料调研

调研日期：2026-10-28。用途：为 x7x24 基于过程数据设计持续改进机制提供研究依据。本文是研究笔记，不代表项目已经实现这些机制，也不是生产有效性的验证报告。来源限于论文原文和作者官方项目；较新的工作按预印本结果理解，没有在本项目复现实验。

## 1. 先区分要改进的对象

工程上建议使用下列分层，避免将日志增多、反思次数增多直接计为 RSI。这是本次设计采用的分类，不是一个统一的学界标准。

| 层次 | 被改变的对象 | 持久化产物 | 可以证明什么 |
| --- | --- | --- | --- |
| 单任务修正 | 本次答案、实现、行动序列 | 本次任务的修订版 | 该任务通过返修改善 |
| 经验积累 | 可检索记忆、领域知识、技能 | 带适用条件的经验条目、可执行技能 | 后续任务可能复用经验，仍需效果对照 |
| 任务 agent 演进 | prompt、上下文策略、工具、工作流、agent 代码 | 不可变的 agent / policy 版本 | 新版本在独立任务上表现改善 |
| 改进器演进 | 诊断方法、候选生成、实验选择、搜索策略 | improver / meta-skill 版本 | 在相同起点与预算下，更有效地产生后续改进 |
| 模型训练 | 权重、适配器、训练算法 | 可部署的模型检查点 | 模型参数发生学习；本身仍不足以证明改进器变好 |

Reflexion 明确通过语言反馈和情景记忆改善后续尝试，不更新模型权重；Voyager 将经过执行反馈改进的代码纳入可复用技能库。它们提供了前两层的基础，但不能仅凭有记忆就推断改进过程本身已经改善。[Reflexion 原文 §3](https://arxiv.org/html/2303.11366v4#S3)、[Voyager 官方项目](https://voyager.minedojo.org/)

更接近严格递归的问题是：保留下来的改变是否也提高了系统产生下一次改进的能力。HyperAgents 将可修改的任务 agent 与 meta agent 放入同一程序；2026-10 的评估研究进一步区分最终系统能力、完整循环可重复性和改进器能力，指出这些需要不同的实验设计。[HyperAgents 原文 §3](https://arxiv.org/html/2603.19461v1#S3)、[Auditing the Product, Not the Recursion 原文](https://arxiv.org/html/2610.27610v1)

## 2. 八条最相关的技术路线

### 2.1 ADAS：搜索 agent 的设计，而不只改写一句提示词

**机制与对象。** Meta Agent Search 读取先前候选及其表现，生成实现新 agent 的代码；搜索范围可以包含提示词、工具使用、控制流和模块组合。发现的 agent 与评测结果进入 archive，作为后续设计的素材。论文在 ARC、推理等任务中评测，并检查部分跨模型、跨任务迁移。[ADAS 原文 §2–4](https://arxiv.org/html/2408.08435v1)、[官方代码](https://github.com/ShengranHu/ADAS)

**边界与借鉴。** 在此设计中，meta agent 的搜索程序并未因此自动成为可演进对象。适合借鉴“候选设计 + 执行结果 + 祖先档案”的持久化形式。项目可以先在声明式 pipeline 和角色策略上搜索；这属于任务 agent 演进，不能因此宣称已验证改进器演进。

### 2.2 Darwin Gödel Machine：自改代码与保留多样化祖先

**机制与对象。** DGM 使用冻结的基础模型修改 coding agent 自身代码，以 coding benchmark 的执行结果筛选和积累候选，并从 archive 中选择祖先继续探索。并非只保留最新或单一最高分版本；中间版本可成为后续突破的踏脚石。论文演示的是 agent 代码演进，没有训练基础模型。[DGM 原文 §3–4](https://arxiv.org/html/2505.22954v1)、[官方代码](https://github.com/jennyzzt/dgm)

**边界与借鉴。** 任务和自改过程都依赖编码能力，是其递归收益的重要前提。原文也指出单一 benchmark 不能覆盖所有期望属性，并保留隔离环境、时间限制和修改谱系。项目可借鉴候选档案、可追溯祖先和隔离验证；不能把论文在特定 benchmark 的收益当作项目收益承诺。

### 2.3 GEPA：把执行反馈变成有针对性的策略变异

**机制与对象。** GEPA 从执行轨迹中提取自然语言反馈，诊断失败，提出 prompt 变体并评测；保留在不同样本上有优势的候选，可组合互补的改进。持久化对象是候选文本、祖先及样本评测结果。原论文的 Pareto 选择涉及不同样本的优势，不能简单等同于“成本和质量的二维最优”。[GEPA 论文](https://arxiv.org/abs/2507.19457)、[官方仓库算法说明](https://github.com/gepa-ai/gepa#how-it-works)

**边界与借鉴。** 它是可度量目标下的反思搜索，通常仍采用固定优化过程。适合从代码返修、测试计划、上下文选取等小范围策略开始。项目增加成本约束、多租户隔离或投放控制属于自身工程设计，不是 GEPA 已经替项目解决的问题。

### 2.4 ACE：经验库采用条目化增量更新

**机制与对象。** ACE 将工作划分为 Generator、Reflector、Curator：执行产生轨迹，从成败提取经验，再合并为结构化 context 条目。条目携带标识和 helpful / harmful 计数；通过局部 delta、去重和精炼控制长期积累，减少整体重写造成的信息丢失。评测覆盖 AppWorld 等 agent 场景和领域任务。[ACE 原文 §3–4](https://arxiv.org/html/2510.04618v1)

**边界与借鉴。** 原文承认反思质量不足会产生噪声甚至有害上下文，丰富上下文也不是所有任务的最佳选择。适合项目建立有证据、范围和有效期的经验条目；条目被“引用”或 agent 自报“有帮助”，仍须与实际交付结果分开记录。ACE 本身不等于改进器的递归演进。

### 2.5 HyperAgents：将改进方法也纳入可修改对象

**机制与对象。** DGM-H 结合 task agent 和 meta agent，使产生改进的程序也可以变化；以候选档案延续探索。在编码、论文评审、机器人奖励设计和数学解答评分等任务上研究任务能力与 meta 能力，使用 improvement@k 衡量有限生成次数内的改善，并研究跨域复用。[HyperAgents 原文 §3–5](https://arxiv.org/html/2603.19461v1)、[官方代码](https://github.com/facebookresearch/Hyperagents)

**边界与借鉴。** 外层祖先选择和评估协议仍固定，论文没有展示完全无约束、无穷进步。项目后期可让诊断和候选生成策略演进，同时保留独立评估。实际验证还应固定起始 artifact 和完整状态，避免将更强任务 agent 一同迁入造成混淆；这是本项目建议强化的实验条件。

### 2.6 AIDE²：独立评估要测研究效率，也要测改进器

**机制与对象。** 2026-09 的 AIDE² 在内层用固定预算优化任务代码，外层修改研究 agent 的 harness，以隐藏结果决定保留，另用未参与选择的任务审计迁移能力。改动涉及搜索和上下文管理。适合借鉴“公开反馈、候选选择、最终留出审计”分离。[AIDE² 原文 §2–3](https://arxiv.org/html/2609.26457v1)

**关键反证边界。** 原文 §3.6 用相同起点、两个 outer improver、每组三个种子进行 ignition test，作者明确认为结果不足以确定新 improver 更优。应据此区分“最终 agent 改善”与“改进器更会改进”：前者成功不能替代后者证据。该工作是较新预印本，并非项目内复现结果。[AIDE² ignition test](https://arxiv.org/html/2609.26457v1#S3.SS6)

### 2.7 Skill∞：把改进流程编码为 meta-skill

**机制与对象。** 2026-10-26 的预印本把技能优化程序本身编码为 meta-skill；meta agent 按该流程诊断轨迹、提候选、请求隔离评审并分配预算，同一流程又用于优化 meta-skill。优化后的 meta-skill 与具体 task skill 解耦，供后续任务复用。实验涉及 SkillsBench、KernelBench 及消融。[Skill∞ 原文 §3–4](https://arxiv.org/html/2610.35434v1)

**边界与借鉴。** 原文限制包括冻结基础模型、依赖可靠自动验证，以及长指令遵从缺乏工具级强制。项目可把“经验如何提取、候选如何设计”做成版本化 meta-skill，但权限、评估隔离、预算和晋级条件应由程序执行。该论文刚发布，不能将其结果视作成熟生产结论。

### 2.8 Agent Lightning：为未来权重训练保留接口

**机制与对象。** Agent Lightning 将 agent 运行与训练解耦，通过统一的状态、调用、结果与 reward 数据构造训练 transition，再由训练侧更新权重。论文覆盖 text-to-SQL、RAG、数学工具使用。[Agent Lightning 原文 §3–4](https://arxiv.org/html/2508.03680v1)

**边界与借鉴。** v1 中 episode 回报分给各 action 的实现使用相同最终回报，精细 credit assignment 留待扩展，不能认为已解决多角色贡献归因。项目应先沉淀可对齐的观测、动作、版本和结果，保持训练接口可选；仅使用托管模型 API 的当前系统不必先建设训练集群。

## 3. 评估是独立工程问题

2026-10 的 EvalResearchBench 让 agent 在固定预算下设计和冻结轻量 evaluator，再与公开及密封目标评测比较。它发现开发目标上的最佳 evaluator 未必在密封目标上最佳，并观察到截断答案、预算耗尽、少量题目权重过大等问题。因此让 agent 生成测例很有价值，但不能直接赋予这些测例决定自身晋级的全部权力。[EvalResearchBench 原文 §3–5](https://arxiv.org/html/2610.04184v2)

同月的评估审计研究把“更好的最终系统”与“更好的改进过程”明确分开；其同起点对照要求固定的是完整起始 artifact，而非仅仅相同初始得分。这里采用其方法论提醒，不将单篇新审计论文的统计比例泛化为整个领域的定论。[Auditing the Product, Not the Recursion 原文 §3–4、§8](https://arxiv.org/html/2610.27610v1)

## 4. 对 x7x24 的设计推论

以下为结合论文形成的工程建议，不是论文直接证明的项目事实；项目现状和具体接入点由配套设计文档中的代码核查为准。

1. **保留两层版本。** task policy 版本回答“如何交付”，improver policy 版本回答“如何分析历史并提出改进”。先验证前者，再独立验证后者。可修改 meta-skill 是实现选择；固定 evaluator 也不妨碍研究有边界的递归改进，但仅有固定 evaluator 和反馈循环绝不代表递归改进已成立。
2. **将过程数据整理成 episode。** 一个 episode 关联任务输入快照、目标仓库版本、pipeline / role / skill 版本、上下文清单、工具动作、产物、验证结果和成本。学习对象是可观察决策与执行结果，无需以采集模型内部隐含推理为前提。
3. **先分标签，再谈学习。** 合同产物完成、指令已加载、静态检查通过、真实测试通过、业务验收通过、发布后稳定是不同事实。历史字段无法支撑的标签应为 unknown，不能把所有成功状态当作正例。
4. **经验是带条件的假设。** 将失败归因为可检验假设，记录证据引用、适用仓库 / 技术栈 / 节点、反例、有效期。LLM 总结先进入候选库；只有验证后才可影响稳定运行策略。记录它何时被实际注入，才能测有无使用的差异。
5. **回放是重新运行，不是只读旧日志。** 旧轨迹可用于发现问题；新策略有没有效果，需要在固定输入、代码基线和可控工具环境中重跑。离线模拟、真实工具执行和生产反馈须分别报告，不能把 mock 得分当真实交付率。
6. **控制选择偏差。** 用开发集产生候选、验证集选版本、密封测试集做发布审计。按仓库、任务家族和时间去重隔离，将同一 Issue 的返修、子任务与近重复分在同一侧；被候选搜索反复看到的集合已不能称最终测试集。
7. **预算计入整个改进过程。** 对照固定模型和工具能力，计入反思、候选生成、评审、所有失败运行与评测成本。先比较同预算下的成功率与代价，再做跨模型或更大预算实验，避免把额外计算当成 RSI 收益。
8. **晋级分两个实验。** 任务策略晋级比较旧/新版本在配对任务上的交付结果；meta-skill 晋级则让旧/新 improver 从同一个 task-policy 版本及同一数据快照出发，在相同预算下各跑完整优化过程，再由独立测试比较生成的后代。多次种子或独立运行用于报告不确定性；证据不够时应标注尚未验证。
9. **终局结果优先。** 测试和验收为主反馈，评审意见用于定位问题；上线后回滚、缺陷重开和失效反馈修正延迟标签。重试次数、PR 合并数、LLM 自评分或经验条目数可作诊断指标，不能单独作收益目标。
10. **先演进低成本、可回滚对象。** 优先经验检索、上下文选择、返修提示和测试规划；后续再探索工作流和工具代码。候选生成与自评不得直接修改外层评估、授权、预算和审计结果。每次运行固定版本，晋级原子切换，失败能恢复稳定版。

## 5. 建议保留的三个结论

- 最实用的起点是 **ACE 式经验整理 + GEPA 式策略搜索 + 独立回放评测**。它可以形成持续改进系统，是否成为 RSI 还取决于后续改进器实验。
- 更接近递归目标的方向是 **HyperAgents / Skill∞ 式 meta-policy 演进**。工程中要把可演进策略与外层执行约束分开；存在可编辑的 meta-policy 不等于已经证明它更会改进。
- **AIDE² 的不确定结果应成为验收设计的参考**：敢于报告最终 agent 变好，而“改进器更优”证据仍不足，才能避免将更多数据、更多计算或偶然命中误判为递归收益。
